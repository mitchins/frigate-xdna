Associated state gaps found during inspection (same checkpoints):

- `wait --state verified` and `wait --state active` can never succeed:
  no code path stores `VERIFIED` or `ACTIVE` on a ref
  (`supervisor.py:376` notes "Never VERIFIED, never ACTIVE";
  `activate` returns `"state": "ACTIVE"` only in its response dict,
  `supervisor.py:750`). Every advertised state needs a defined
  predicate and a bounded success/failure path (checkpoint 4).
- No phase/exit/errno evidence is persisted on job failure today
  (`set_job` records stage + error_code only, `jobs.py:112-115`);
  checkpoint 5 extends this to a structured failure record without
  changing the existing terminal-state vocabulary.

## Checkpoint order (low risk → hardware)

0. This matrix (done when committed).
1. Deployment recipe + README (Compose memlock, release-image
   default, both networking variants, credentials, README
   what/why/how).
2. Truthful release identity (dev/RC/stable; sanity compares
   reported vs expected).
3. Scripted vendor-boundary tests (compiler phases incl. the
   `Compilation Complete` + FlexMLRT `mmap flags=8209 err=-11`
   pattern on stdout and stderr; native runtime seam; test-only
   stubs never shippable, release sanity rejects them).
4. State/health/waits/console/preflight (D1, D2, D6, D10, advertised
   states, deployment preflight).
5. Bounded recovery without data destruction (D4, D5, RC3-data
   upgrade, cache/process invariants).
6. Final README + current-model hardware confidence run (30 min,
   fresh install, cached restart, upgrade/recovery at the right
   boundary; no new large-model sweep or power campaign).
7. Qualify and release v0.1.1 (full gates, dry-run, unused
   `v0.1.1-rc.N` only with owner approval, never move/recycle tags).

Existing gates stay in force throughout: hardware-free suite,
coverage/lint/Sonar, SBOM validation, attestations, pre-push and
pull-by-digest checks, `GH_REPO` handling. No gate is lowered to
pass a checkpoint.
