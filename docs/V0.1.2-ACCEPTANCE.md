# frigate-xdna v0.1.2 — acceptance matrix

Tracked task/acceptance document for the v0.1.2 release: first-class
local YOLO ONNX as an appliance workflow equal in usability to
Frigate+.

Starting point: `main` at `d96fbbcb27b2c95f0648787d0f99264dfa223ab8`
(v0.1.1 close); verified 2026-09-24 — no intervening changes.

v0.1.1 behaviour and release invariants are preserved throughout.
`v0.1.1` / `v0.1.1-rc.1` tags are never moved or recycled. No new
AMD/runtime dependency versions for this feature; any such proposal
stops for separate justification.

This is not a general ONNX framework and not a model-zoo/downloader
project.

## Checkpoint 0 — frozen upstream contract (this document)

No implementation changes. The upstream facts below were verified
against Frigate's current documentation (object-detectors page,
2026-09-24) and the stock ZMQ detector contract.

### Frigate local YOLO (reference configuration)

Frigate treats local YOLO ONNX as a normal first-class configuration.
Its documented YOLOv9 setup (OpenVINO, ONNX, and Apple-Silicon/ZMQ
sections all repeat the same model block) is:

```yaml
model:
  path: /config/model_cache/yolo.onnx
  model_type: yolo-generic
  width: 320
  height: 320
  input_tensor: nchw
  input_dtype: float
  labelmap_path: /labelmap/coco-80.txt
```

Facts frozen for 0.1.2:

- YOLOv9 is Frigate's recommended ONNX model; sizes `t/s/m/c/e`,
  common exports `320` and `640`.
- `width`/`height` must match the actual export geometry. 320 is the
  recommended initial qualification target and remains
  Frigate-optimized (motion-crop zoom before detection); 640 or other
  geometries are not implied merely by accepting the graph.
- Frigate's documented export route is the WongKinYiu/yolov9
  `export.py --simplify --include onnx` Docker recipe. For
  obtaining/exporting YOLOv9, link to Frigate's official instructions;
  do not duplicate their export recipe.
- Frigate owns the label map (`/labelmap/coco-80.txt`).
  frigate-xdna preserves numeric class IDs and exposes inferred class
  count, but must not invent labels or rewrite Frigate's semantic
  configuration.

### ZMQ

The Apple-Silicon section documents the same local-YOLO model contract
over a `type: zmq` detector — this is our sidecar's integration point.
Stock Frigate transfers the local ONNX bytes when the external
detector does not claim the model is already loaded, and only marks
the detector ready after the model-transfer/load handshake succeeds.
Therefore:

- local pre-preparation and later Frigate transfer must converge on
  the same source hash and existing compiled artifact;
- no basename may become an identity (wire names are alias hints
  only — already the rule in `models/refs.py:wire_alias`);
- model operations use bounded 30-second windows: Frigate 0.18 sets a
  30-second receive timeout for the model-availability response and
  separately for the model-transfer response — per response, not one
  total initialization deadline. Eager pre-compilation keeps us
  comfortably inside both.

### Export compatibility

Ultralytics' official ONNX exporter defaults are broadly compatible
with what we want: batch 1, static dimensions unless `dynamic=True`,
graph simplification, and `nms=None` producing raw predictions for
external NMS. But that does not mean every YOLO generation/output
head matches our current `[1, 4+C, N]` contract
(`models/inspect.py:classify_output` accepts single raw-YOLO tensor
`[1, 4+C, N]`, float), so compatibility is inspected and reported,
never guessed.

For Ultralytics exports, one sentence is enough: use a static
batch-one FP32 ONNX with raw predictions; the sidecar inspects the
graph and refuses unsupported output contracts before compiling. Link
to the official export documentation.

Explicitly out of scope unless a mandatory public target requires it:
embedded NMS, multi-head/multipart legacy YOLO, YOLOX, YOLO-NAS,
segmentation, pose, classification, dynamic input shapes, INT8 input,
FP16 input, external ONNX tensor data.

### Supported-contract definition for 0.1.2

Two equal acquisition paths:

```text
plus://MODEL_ID        (Frigate+ fetch; v0.1.1 behaviour unchanged)
local://MODEL_ID       (operator-supplied ONNX; new in 0.1.2)
```

Both become: exact source bytes → SHA-256 source identity → serving
contract → compile key → cached artifact. The human-readable ID is an
alias/desire declaration; content remains the authoritative identity.
The content-addressed design is not weakened to make local models
easier.

`local://ID` mapping (checkpoint 1):

```text
local://yolov9-t-320  →  ${FXDNA_MODEL_DIR}/yolov9-t-320.onnx
```

- `FXDNA_MODEL_DIR` defaults to `/models` in the appliance.
- IDs are conservative single components:
  `[A-Za-z0-9][A-Za-z0-9_.-]{0,127}`. No `/`, `..`,
  percent-encoded traversal, URI authority, query string, or
  arbitrary URL.
- Never recursively scan the model directory and compile whatever
  appears there. `FXDNA_MODELS` is desired state.
- The existing explicit path interface (`/models/foo.onnx`) shipped
  in 0.1.1 and remains an advanced/compatible path.
- `local://ID` is an operator-controlled mutable alias: changed bytes
  under the same ID are a new model revision (new source SHA, new
  artifact, old artifact preserved, no silent worker switch —
  checkpoint 5).

Compatibility target (checkpoint 3/4): static batch-one float32 NCHW
input, single raw-YOLO output tensor (layout recorded in the serving
contract, including an explicit adapter only if a mandatory public
target needs the common `[1,N,4+C]` transpose). All incompatibility
is reported before compiler invocation with stable reasons; label
names are never inferred.

## Checkpoint order (low risk → hardware)

0. This matrix (done when committed).
1. First-class local model references (`local://ID`,
   `FXDNA_MODEL_DIR`, alias-is-mutable semantics, path containment).
   Exit: parser/path-containment/update tests green.
2. Canonical local Compose overlay (`examples/compose.local.yaml`
   parallel to `compose.plus.yaml`; read-only model mount; Portainer
   same three values; no Plus credential). Exit: Compose rendering
   tested, read-only mount proven, no Plus credential required.
3. Compatibility inspection as appliance UX (normal logs/status
   report input/output/classes/contract or an immediate useful
   refusal; same inspector as preparation — no duplicate validator;
   machine output carries identity/geometry/layout/class_count/
   compatible/reason). Exit: all compatibility failures happen before
   compiler invocation, stable regression tests.
4. Qualify actual YOLO contracts (A: public YOLOv9-t 320 via
   Frigate's documented export route, frozen fixture/manifest; B:
   existing YOLOv8n evidence through the local route; C: one current
   Ultralytics raw export, transpose adapter only if required and
   recorded). Exit: every claimed family backed by a real public
   graph fixture and contract test.
5. Desired-state/cache/state correctness (`local://foo` and
   `zmq-upload:<same SHA>` converge; multi-alias/rename/changed-bytes/
   missing/unreadable/escape/unsupported/absent-source restarts;
   mixed local+Plus; no Plus HTTP for local refs; no recompile on
   Frigate reconnect). Exit: state/cache regression suite green.
6. Concise README local-YOLO path (both users on the first screen;
   link — don't duplicate — Frigate export docs; factual
   compatibility table only after acceptance; no marketing prose).
   Exit: a non-Plus user follows the README without architecture
   docs.
7. End-to-end non-Plus hardware acceptance (no `PLUS_API_KEY`: fresh
   `/data`, public YOLOv9-t-320 read-only, inspect → compile →
   validate → PREPARED → stock Frigate 0.18.0 local ONNX → cache hit
   → ACTIVE/ready → real detections; same-ID revision switch
   correctness; 15–30 min confidence, no new 24 h soak). Exit: all
   acceptance predicates true on the certified Strix Halo system.
8. Release 0.1.2 (dry-run → next unused RC → published-image pull →
   local-YOLO installed smoke → stable 0.1.2). Exit: stable release
   published, 0.1.1 tags untouched.

Existing gates stay in force throughout: hardware-free suite,
coverage/lint/Sonar, SBOM validation, attestations, pre-push and
pull-by-digest checks. No gate is lowered to pass a checkpoint.

## Explicit non-goals

Not a public model repository, automatic Internet model downloading,
automatic label-map generation, arbitrary ONNX support, a training
workflow, an Ultralytics dependency in the runtime image, a general
tensor RPC, another Frigate detector plugin, a broad PEAK/model-size
campaign, power benchmarking, or new hardware certification.
